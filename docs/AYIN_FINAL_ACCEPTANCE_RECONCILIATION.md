## Viewport, keyboard and RTL acceptance boundary

- Actual repository Playwright configuration runs Chromium (`playwright.config.ts`). A resized Chromium page is not iOS Safari, Android WebView, a physical TV or OS installation.
- Shared navigation has explicit 360, 390, 768, 1440 and 1920 widths; its matrix is not the Cartesian product with both languages. The broad responsive test visits many routes at 390, eight representative routes at 768, and nine at 1440. “No document overflow” is a necessary assertion, not complete visual readability or keyboard acceptance.
- Focused modern consumer/editor suites generally use EN/AR at 390 and 1440, with targeted long-content, actual control bounds and independent original-image review recorded in their evidence. Some inherited tests are English-only or only exercise one narrow viewport. Do not label every route as EN/AR × every width accepted.
- Keyboard evidence specifically exists for navigation modal containment/restore, remote geometry, resizing an open dialog, native confirmation/EditorTabs, public hero/detail controls, Studio pagination and merchandising selection. Shared primitive tests support other consumers but do not prove every dense editor's full keyboard journey.
- Finite closing sample: for each materially changed family in this release, inspect its actual final-head EN/AR390/1440 originals; replay one keyboard-only critical path through its primary action/error recovery. At 360, 768 and 1920 test shared shell/nav plus representative dense table/editor/player, not every identical route template. Include long Arabic/Latin authored content, fixed-nav occlusion, browser Back/Forward, hidden/visible recovery and cancellation. Preserve the distinction between covered, newly passed, not run and external.

## Mobile architecture and readiness

Preserve the existing justified split. Android mobile/TV/Fire APK is a hardened HTTPS WebView shell reusing Web authentication, focus, media, consent and API behavior. iOS is SwiftUI + AVPlayer/AVKit with native discovery, bearer/Keychain authentication, progress, native sharing, PiP/AirPlay and narrow Safari fallbacks. It is not a full-site WKWebView wrapper and should not be replaced merely to make the platforms look identical.
