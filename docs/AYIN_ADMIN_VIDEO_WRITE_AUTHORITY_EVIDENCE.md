# AYIN Admin video commit authority evidence

The actual Admin video service updated video metadata/status/visibility/comments/TV preferences and audited in a transaction, but relied on a pre-handler actor account ID. A revoked role, actor session or MFA version could win a lock wait and still allow the command. Directory count/items used separate snapshots and unstable updatedAt-only ordering; the UI had no direct original-record recovery or optimistic target version. Bulk writes silently skipped removed rows and could acknowledge a partly changed selection.

Video commands now capture the authenticated actor and reuse the existing held credential/Account/role/session/step-up authority helper with explicitly scoped OPERATIONS/CONTENT_MODERATOR roles. SUPERADMIN/ADMIN retain their existing privileged MFA requirement. The helper default remains OPERATIONS for accounts/TV; this does not grant moderators those domains or generic staff privileges. Actor authority is checked before sorted Video row locks and again after their wait, including actual database session expiry and current reauthentication time. Authority and target rows remain held through video/preferences/audit commit.

Optional strict ISO expectedUpdatedAt preserves legacy callers; clients adopting optimistic edits always supply it. Stale versions reject409, missing originals404 and malformed controller IDs400. Versions advance beyond both the current clock and any future previous timestamp. Bulk expectedVideos, when supplied, must contain exactly one unique version for every normalized selected ID. All selected rows are locked in UUID order; one missing, newer or removed row rejects the entire selection before update or audit. Removed records remain readable for recovery but cannot be resurrected through the ordinary editor. One bulk version exceeds every prior selected version; one audit commits atomically. Existing100-target cap and legacy verified unpublish commands remain.

Directory count/items share RepeatableRead and updatedAt/id ordering. A direct safe projection read returns actual metadata, channel, TV preferences and counts without credentials or raw media secrets. Controller directory/direct/command responses declare private/no-store/Pragma; unknown filters reject400. This is the existing projection, not a bounded preference-history redesign; current TV inclusion destination selection needs separate native editor review.

Twenty prepared real AppModule/PostgreSQL cases cover sixteen observed actor/MFA/session/role/target/clock winners across both individual and bulk commands, stable26-row25+1 directory/direct projection/Finance denial, actual Content Moderator editing without account/TV permission, atomic stale/removed bulk decisions with complete version coverage and one successful audit, and real audit-trigger rollback of both video and TV inclusion followed by one explicit retry. The actual database must execute these tests before acceptance; local type/lint/format or prepared fixtures are not passing integration evidence.

This backend slice does not repair the old prompt-based video UI, certify every policy/owner/provider transition or complete master phases7/8/13/14. Native localized video forms, independent draft retention, strict acknowledgments, whole-operation identity/freeze handling, explicit bulk/original-record recovery and real browser/visual acceptance remain required. Exact-source full gates and review are pending; no release or whole-master completion is claimed.
