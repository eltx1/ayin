# Native decoded Watch startup laboratory

This separate Phase 10 workload measures the real Watch player with the existing synthetic `clips-viewport.webm`: 30-second VP8 at 96 × 160, temporarily staged under a dedicated local Next public path. The dedicated server wrapper verifies those exact bytes before startup, refuses an existing staging directory, and verifies content again before removing its generated file/directory on graceful shutdown. The external run controller must independently assert that the path is gone and retain that cleanup result. No duplicate public production asset is committed and the existing CSP remains unchanged. The real API/PostgreSQL fixture retains the existing MP4 canonical declaration required by production policy; the browser-only fixture substitution follows accepted Clips acceptance and delivers the exact WebM as `video/webm`. This is explicitly a native front-end decode workload, not proof that a valid production MP4 was generated. Only that synthetic object's recorded fixture-alias URL (`http://media.invalid` or the compiled build's local Next origin) receives an empty 307 redirect to the allowed same origin, `http://127.0.0.1:3000`; Chromium transfers the media response itself, with byte ranges and the recorded CDP network limits. Media bytes are not supplied by Playwright fulfillment, and native media prototypes, play events and frame readiness are never replaced.

Each of the original desktop/constrained profiles uses three fresh authenticated contexts with cache disabled and Service Workers blocked. Trace and screen-video recording are disabled for the resumed measurement to avoid capture overhead and raw network trace retention; earlier unsuccessful attempts inherited retention-on-failure. Their failed samples remain separate. The test records separate route DOM readiness, navigation-to-first-observed-frame, trusted-Play-click-to-`playing`, and trusted-Play-click-to-first-observed-advancing-frame. Native frame callbacks, media events, dimensions, duration, media errors, resource status/counts and local HTTP range/declared-length observations remain raw. A native frame callback indicates decoded-frame presentation scheduling, not physical display latency. The collector preserves the final player’s actual autoplay request and records its native preload setting. It first observes automatic advancement for up to ten seconds. Only a still-paused, error-free player with its real Play control then receives a trusted click; this is a labeled fallback, not an inferred browser-policy rejection. Automatic samples have null trusted-click durations. An initial preloaded frame may precede Play, so fallback click-to-playing is not a cold-download measurement.

This is one small synthetic WebM served by local Next static HTTP. It does not certify production MP4/HLS encoding, ABR, remote R2/CDN delivery, advertising, upload transfer, concurrency, physical devices or field percentiles. Declared response lengths, CDP transfer completion and successful native frames are recorded separately; none is relabelled as another. The route-ready unavailable-media baseline remains a distinct experiment.

Source, fixture SHA-256, Node/Chromium, exact profile, runtime source declarations, native observations and successful/failed/in-flight resource counts are retained in `performance-baseline-decoded-*.json`, covered by the existing controlled-runtime artifact upload. Partial failures retain completed samples and cannot be presented as a successful run. Targeted TypeScript, ESLint, formatting and Playwright discovery pass; final application build handoff and actual browser measurement are still queued. No startup number or improvement is claimed yet.

The queued continuation will use the final accepted Playback policy source/build handoff. Earlier unsuccessful attempts on the historical Search build remain separate; no successful native samples have yet been attributed to either build.

The exact fixture has one VP8 video stream and no audio stream (verified with ffprobe), so automatic-startup observations do not establish audio autoplay behavior. Advancing readiness requires two observed frame callbacks with increasing mediaTime; a single decoded frame at a positive saved resume position is insufficient. Fresh contexts reuse one synthetic profile per configured profile, and actual media positions remain in the report. Web and API compiled-source declarations are retained separately when their accepted build commits differ; this accepted Watch/Search authority build is not relabelled as a later complete master union.
