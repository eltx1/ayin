# Deletion cancellation: current authority and lifecycle lock order

Cancellation previously accepted only the account ID captured by AuthGuard. Revocation, suspension, credential-version change or session expiry while the command waited could therefore leave a stale authenticated request able to cancel deletion. The service now accepts the actual captured authentication context, holds Account FOR UPDATE then the current AccountSession FOR SHARE, and revalidates active account, ownership, captured account/session auth versions, revocation and actual clock expiry before changing the deletion request.

The current cancellable request is selected inside that transaction, its row is locked and state reread. Expiry is checked again after a possible request-row wait. Only REQUESTED/GRACE_PERIOD can become CANCELLED, the timestamp is created after the wait, and the audit records the actual locked prior state. Cancellation and audit commit together. No new password/MFA/step-up requirement is introduced. Session and account locks remain held through audit completion.

Lifecycle deactivation, anonymization and administrative recovery now take the account lock before their request mutation. This preserves account-before-request order shared by cancellation and request creation; leaving workers request-first would allow a deadlock with cancellation waiting on their request row while they waited on its account. Grace transition and lease claims operate on request rows without later acquiring account/session locks. Existing lifecycle predicates, leases, financial retention, media cleanup and administrative recovery policy remain unchanged; this focused change does not certify administrative actor authority under lock or legal deletion.

Thirteen actual PostgreSQL cases are authored: seven independently observed held-account-row winners (account status/auth version, session version/revocation/expiry/deletion and actual clock expiry); actual audit insertion failure with full cancellation rollback followed by explicit one-time retry; two concurrent authenticated cancellations with one success/one conflict and one audit; a winning terminal request state; actual expiry while waiting specifically on the request row; and both cancellation-first and actual deactivation-worker-first lock races. Tests use real registration, cookies, database writes, pg_stat_activity lock observations and the real lifecycle service, without replacing AuthGuard. They are not execution proof until owning CI passes.

Local API source tests, API production declaration build, full API types, focused lint and formatting are required before publication. Existing privacy lifecycle integration coverage remains part of the owning regression gate. Physical device behavior, field performance, retention certification and all 17 master phases remain open.
