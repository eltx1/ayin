# AYIN Creator TV — FAST / Linear Streaming Architecture

Task 35 upgrades Creator TV from an application-scheduled progressive-MP4 experience toward a true provider-backed linear channel without removing the existing VOD fallback.

## Repository-side architecture

`CreatorTvLinearService` derives a deterministic linear channel plan from the same Creator TV schedule already used by AYIN. The plan contains:

- ordered programs with wall-clock start/end times;
- R2 object-key source references for the existing rights-cleared MP4 assets;
- XMLTV EPG output;
- ad-break markers emitted as `SCTE35_INTENT` metadata so a future packager/SSAI system can translate them into the provider-specific signaling format;
- an explicit progressive-MP4 fallback that remains enabled.

The `LinearStreamingProvider` interface is the only component allowed to provision/reconcile/stop a real linear output. A provider implementation is expected to turn the plan into continuously packaged HLS and return the real HLS URL/resource identifier. The default production binding is intentionally `UnconfiguredLinearStreamingProvider`; it never fabricates a stream URL.

## HLS and packaging boundary

AYIN does not claim that Cloudflare R2 performs live/linear transcoding or packaging. R2 remains the source-object/VOD store. A real linear provider or owned compute pipeline must ingest the referenced MP4 objects, maintain wall-clock playout, package HLS, handle discontinuities and refresh the schedule.

A future provider adapter must implement:

1. `getState(tvChannelId)`
2. `provision(plan)`
3. `reconcile(plan)`
4. `stop(tvChannelId)`

The adapter must return only a real HLS URL generated by the selected provider/compute layer.

## EPG

`GET /public/channels/:handle/tv/linear` returns the current XMLTV guide alongside provider state and fallback details. XMLTV is generated from the same schedule used by the public Creator TV surface, so Admin schedule changes remain authoritative.

## Advertising / future SSAI and Google DAI

Existing `CreatorTvAdBreakHook` output is carried into the linear plan. Each break is represented as an `SCTE35_INTENT`; this is metadata, not a claim that SCTE-35 has already been inserted into a transport stream.

A real packager/provider adapter may later map the marker to:

- SCTE-35 splice markers;
- provider-specific SSAI cue points;
- Google Ad Manager DAI stream-event/ad-break configuration.

Client-side IMA and existing house/direct fallbacks remain untouched. Task 36 owns real Google Ad Manager account integration.

## Operational endpoints

Channel owners can inspect/provision/reconcile/stop linear output through:

- `GET /creator/tv/:tvChannelId/linear`
- `POST /creator/tv/:tvChannelId/linear/provision`
- `POST /creator/tv/:tvChannelId/linear/reconcile`
- `POST /creator/tv/:tvChannelId/linear/stop`

All owner authorization still flows through the existing Creator TV management authorization. Existing Admin schedule overrides, status controls and ad controls remain the source of truth; linear plans are derived from those resolved schedules rather than maintaining a competing schedule database.

## External production prerequisites

Repository-side orchestration is complete without inventing a provider. Production verification remains blocked until AYIN has a selected linear streaming provider or compute plan plus credentials/budget. Live verification must then cover:

- source retrieval from R2;
- continuous HLS packaging and manifest refresh;
- schedule transitions and discontinuities;
- real-device playback/recovery;
- EPG synchronization;
- ad-marker translation;
- SSAI/Google DAI integration if enabled;
- failover to progressive MP4 when the linear provider is unavailable.
