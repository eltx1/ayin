## Web updates and cache boundaries

Android loads the production HTTPS website, so normal navigation loads server releases. This is an online website architecture, not an atomic downloadable offline bundle updater. The baseline PWA worker (`apps/web/public/sw.js`) stores a neutral offline page and at most 128 build assets, excludes API/document caching, and uses explicit activation/reload prompts. `service-worker-registration.tsx` does not distinguish the Android shell from a PWA at baseline. Native shell cache ownership must be separated. The offline page is not a fully working cached app, and neither signing, bundle compatibility gates, staged local activation nor last-known-good bundle rollback exists at baseline.

The iOS SwiftUI interface changes require a store binary; server content and Safari-hosted pages update remotely. Converting selected trusted pages to an embedded WebKit surface is a product/architecture change requiring origin checks, session isolation, capability versioning and store review. Do not copy Keychain tokens into URLs, web storage or arbitrary JavaScript. A same-origin XSS can still invoke a trusted-origin bridge; origin checks do not replace normal web security.

## Current platform requirements checked

Official sources checked 2026-10-19:

- [Google Play target API policy](https://support.google.com/googleplay/android-developer/answer/11926878): new mobile submissions/updates require Android 16 / API 36 since August 31, 2026. TV and other categories have separate thresholds.
- [Android 16 KB support](https://developer.android.com/guide/practices/page-sizes): verify native dependencies and the final APK/AAB on a 16 KB environment where native libraries apply; a JavaScript test cannot establish this.
- [Apple upcoming requirements](https://developer.apple.com/news/upcoming-requirements/): Xcode 26 and the relevant version 26 SDK are required for App Store Connect uploads since April 28, 2026; updated age-rating answers must also be completed.
- [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/): 1.2 requires UGC filtering/reporting/blocking/contact; 2.5.2 constrains downloaded functionality; 4.2 requires adequate app utility; 4.7 is not a general exemption for a remotely mutable native bridge. Explain the shipped web/native boundary to review; do not hide functionality or enable undisclosed features after approval. Kids advertising/analytics treatment needs special care.
- [Google dynamic code policy](https://support.google.com/googleplay/android-developer/answer/16559646): interpreted WebView JavaScript is distinguished from downloaded executable code; it still must comply with all policies and cannot expose untrusted content to Android interfaces.
- [Google UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937): publicly accessible UGC needs in-app reporting and blocking.
- [Google account deletion](https://support.google.com/googleplay/android-developer/answer/13327111) and [Apple deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/): provide accessible account/data deletion paths and a valid external deletion resource where required.
- [Google Data Safety](https://support.google.com/googleplay/android-developer/answer/10787469): declarations must include actual SDK collection/sharing, not merely AYIN's manually logged events.

## UGC blocking implementation after baseline

This release adds `UserBlock`, an authenticated account-wide list/block/unblock API, strict channel/profile targets, current-session mutation checks, a no-self-block database constraint, and bidirectional interaction restrictions. Blocking removes existing subscriptions in both directions and closes their analytics subscription episodes; unblocking does not silently restore subscriptions. Signed-in channel/community reads and video-comment reads enforce blocks; comment replies/reactions and subscriptions check the relation. The notification feed suppresses queued messages identified with blocked senders, channels, profiles or videos. Web controls expose channel blocking, comment-author blocking and account unblocking. Mobile push separately checks blocking before delivery.

Blocking is an account safety preference, not a confidentiality restriction on already-public content: anonymous content remains public. Server-rendered anonymous catalog previews cannot infer an API session; authenticated client controls must enforce the relevant channel/interactions boundary. This change does not claim that every public discovery preview has been removed from every native/SSR cache. Already-delivered OS notifications cannot be recalled. A request already in flight when blocking begins may finish; subsequent reads and interactions enforce the new relation.

Local verification: 20 focused unit tests passed across block contracts, comments availability and optional authentication. The new four-case real-PostgreSQL suite is `apps/api/test/user-blocks.integration.test.ts`; no local PostgreSQL service was available, so a real run must be established by CI before treating that suite as passed. The release report should record its exact commit/run result. No physical-device UGC test has been represented as performed.
