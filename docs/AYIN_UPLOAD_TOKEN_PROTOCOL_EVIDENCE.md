# Exact bounded upload-session token protocol

The actual V1 verifier previously split token text into two variables and ignored trailing segments. A correctly signed token with an extra segment therefore remained accepted. Verification now requires exactly two unpadded base64url segments, a 43-character SHA256 signature and a total bound of 16 KiB before HMAC/decoding. Signature comparison remains constant time. Canonical decoded payload bytes must round-trip to the same base64url text; strict UTF-8 and JSON parsing reject malformed content. The strict V1 schema rejects unknown fields, unsafe/nonpositive integer quantities, oversized multipart IDs and disagreement between single/multipart mode and original upload ID. Signing validates the same schema. Continuation HTTP schemas enforce the same size bound before invoking upload services.

Nine local protocol unit cases passed, including actual single/multipart signed round-trips with administrator provenance, the previous extra-segment bypass, oversized/padded/malformed input, modified or wrong-key authenticators, authentic malformed UTF-8/JSON/schema, unsafe numeric/type values, mode-ID disagreement and exact expiry boundary. Full local API source suite passed 98 files/417 tests. API production declaration build/full types, focused lint and formatting are required before publication.

Eight additional actual PostgreSQL/API cases are authored in the existing media upload integration suite: trailing-segment, oversized and authentically signed unsafe tokens each must reject across authorize-part/resume/complete/abort with unchanged real MediaAsset rows and zero provider calls; a valid V1 token must preserve explicit part authorization and resume. Four further cases require metadata after successful multipart completion: wrong size, wrong type and missing object must preserve actual pending rows and create no processing job; lost provider completion response may recover only from matching final metadata, and explicit duplicate completion must produce one processing generation. Fixture source assets are linked to actual isolated pending videos before continuation commands. Real registration/AuthGuard/database remain active. Storage is the existing controlled adapter, so these are API/database boundary cases, not physical R2 proof. They remain authored until owning CI executes.

Successful multipart completion now verifies final object size and known content type before marking UPLOADED, matching the existing single-upload boundary. The previous uncertain-completion recovery uses the same final metadata without an automatic provider replay. This proves neither full-file hash identity nor actual physical R2 bytes with the controlled adapter.
